# 按表「数据更新」实现与验收交接

二期已补充手写建表入口、结构检查和任务组执行，参见 `table-data-update-v2-handoff.md`。下文保留独立任务的一期说明；加入任务组后由组的批次和依赖规则管理。

入口：数据准备 → 数据源 → 数据源表 → 每行的「数据更新」。拥有 `ETL_ACCESS` 的管理员可配置和执行。旧的「集成中心 → 数据刷新」继续保留，新版使用独立配置、运行记录和调度任务。

## 功能范围

- 支持 MySQL、PostgreSQL、SQL Server 数据源。每个数据源内的每张表独立保存配置，不依赖既有三表案例、表名、35 天窗口或固定金额基线。
- **完整 SQL 脚本**：在目标数据源执行一组 JDBC SQL 语句，SQL 自行决定写入逻辑。目标表是配置归属；脚本可以操作中间表。SQL 编辑器不提供 Python、Shell、存储过程编写或客户端 `GO` / `DELIMITER` 命令执行能力。
- **查询抽取**：在选定查询数据源执行一条 SELECT / WITH 查询，按列名映射到当前目标表。源与目标可以不同数据库类型。查询字段用 AS 与目标字段名准确对应；目标表需要预先存在。
- 查询抽取支持全量替换、时间窗口覆盖、按单字段或复合主键更新。按主键更新只改查询包含的非主键字段，其余已有字段保留；缺少的行插入。重复或空主键拒绝写入，由 SQL 明确业务去重规则。
- 手动运行支持指定业务日期；自动调度支持每天或 Quartz Cron，以及所有上游完成后的依赖触发。调度开关、时区、超时、抽取行数上限按表保存。
- 运行记录显示触发类型、业务日期、配置版本、时间、处理行数、结果和失败信息；支持取消。配置有版本冲突检查，运行期间不能修改或删除；被其他任务依赖的配置不能删除。
- 本期未加入 URL 触发、自动重试，符合本次确认范围。

## 查询抽取与跨源边界

每个任务选择一个查询数据源和一个目标表。数据库本身能执行的同服务器跨库 JOIN 可以写入查询；不同服务器的多源 JOIN 需要先把各来源抽取到中间表，再通过上游依赖执行汇总任务。

查询结果先流式读取、分批写入目标连接的临时表。全部抽取完成并通过校验后，才在目标事务中替换/覆盖/更新业务表。默认拒绝空结果；勾选允许空结果后，全量策略会清空目标表，窗口策略会清空该窗口。MySQL 查询抽取目标必须是 InnoDB 实表。

SQL Server 临时表创建避免继承 identity 属性；目标写入含 identity 字段时按需启用 `IDENTITY_INSERT`。PostgreSQL 显式写入 identity 字段使用 `OVERRIDING SYSTEM VALUE`。identity 字段若用于按主键更新，需包含在匹配主键内。PostgreSQL 序列不因导入显式 ID 自动推进；若目标后续还依赖序列生成 ID，可用完整脚本维护序列。数据库专有的复杂字段类型需要在 SELECT 中转换为目标数据库可接受的 JDBC 类型。

源库和目标库之间没有分布式事务；目标库写入具有本地事务边界，读取期间的源库一致性由源连接的数据库隔离级别决定。目标表上的外部写入、触发器、约束和索引遵循数据库自身规则。

## SQL 参数与窗口

- `{{window_start}}`：业务日期向前 N 天的 `00:00:00`，包含单引号。
- `{{window_end}}`：业务日期的 `00:00:00`，包含单引号。
- `{{target_table}}`：按目标数据库方言转义、带目标 schema 的表名。

参数外不要再次加引号。窗口为 `[window_start, window_end)`，不包含业务日期当天。业务日期默认按任务时区计算；SQL 中的时间比较遵循数据库字段类型与会话时区。查询抽取的窗口覆盖模式要求所有查询结果的窗口字段非空且位于该范围。

例如，SQL Server 查询抽取的查询可以是：

```sql
SELECT order_id AS order_id, sale_time AS sale_time, amount AS amount
FROM dbo.orders
WHERE sale_time >= {{window_start}}
  AND sale_time < {{window_end}};
```

SQL Server 源表名应写明 schema。PostgreSQL 连接使用数据源中配置的 schema。目标 schema 从数据源配置读取，页面只读；数据源 schema 改变后，应删除旧更新配置再重新配置。

脚本使用分号分隔语句。支持标准单引号字符串、双引号/反引号/方括号标识符、行注释和块注释。字符串中的单引号用两个单引号转义；注释使用 `-- ` 或 `/* */`，SQL Server 临时表名写为 `[#name]`。执行器管理事务；DDL 及脚本调用产生的外部副作用可能已提交，取消或失败后需检查再手动重跑。

## 调度、依赖与中断

1. 配置保存后，自动调度在 30 秒内同步；运行队列每 5 秒扫描，当前实例最多执行两个任务。
2. 每次运行保存完整定义和上游运行 ID；后续修改配置不会改变历史运行的 SQL、窗口或依赖快照。
3. 手动、定时和依赖触发都要求同一业务日期的每个上游在当前配置版本下成功。定时触发遇到上游未成功或同表已有运行时，记录 `SKIPPED`，本次不补跑。需要等待上游的任务应选择「上游完成后」。
4. 依赖触发关注配置保存后上游新成功的业务日期，并按上游成功运行组合去重。失败/取消后不自动重试；可以手动运行，或等待上游新的成功运行。保存前的历史上游结果不会自动产生一批回补任务。
5. Quartz 设置为跳过停机期间错过的时间点。已经持久化的 `QUEUED` 请求由所属实例继续处理；已开始但进程消失的 `RUNNING` 记录标为 `INTERRUPTED`，不会自动重放脚本。
6. 同一数据源表的更新请求串行执行。元数据库会话锁、锁存活检查、取消监控及提交前检查共同保护执行流程。不同数据源 ID 指向同一个物理表时，应统一使用一个数据源配置管理更新。
7. 新旧功能相互独立。旧任务/外部脚本不会自动关闭；将某张表交给新版调度时，验收人员需先关闭该表原来的自动更新，避免两个系统同时写入。

## 配置与权限

- 本地使用独立 `COMPANY_BI_INSTANCE_ID`；ECS 可使用已有实例标识解析机制。不同环境使用不同标识。复制元数据库不会自动启用复制过来的任务；在新实例保存并开启配置后才接管自动调度。
- 运维开关 `COMPANY_BI_DATA_UPDATE_HARD_DISABLE=true` 停止新版执行，与旧 ETL 开关分开。
- 接口位于 `/company/etl/data-update`，沿用 ETL 管理员过滤器，每个接口再验证 `ETL_ACCESS`。
- 保存、手动运行、取消、删除记入审计。审计只写 SQL 哈希和配置摘要；数据库异常不把原始 SQL、连接字符串或密码写进运行消息。
- 新增 `company_data_update_task`、`company_data_update_run`、`company_data_update_guard` 三张元数据表，应用启动时由现有 schema initializer 创建。
- 保存/删除配置只改变任务配置；删除保留元数据库中的历史运行快照，重新创建会获得新的任务 ID。

## 后续本地验收清单（本轮未执行）

1. 启动后确认三张元数据表创建、表列表入口可见、非管理员无访问权限、旧页面仍可使用。
2. 用任意新命名的测试表验证三种写入策略，再用既有三表案例验收；SQL Server → MySQL 至少跑一条真实跨源抽取。
3. 验证中文/特殊字符字段名、decimal 精度、NULL、日期时间、identity，以及目标表约束。对 PostgreSQL 和 SQL Server 目标分别做方言验收。
4. 验证空结果保护、重复主键、超行数、目标写入中途失败时事务回滚，确认业务表没有半成品。
5. 验证逐表不同时间、业务时区、同业务日期上游链、手动回补、配置版本冲突、同表重复触发、跳过记录和取消。
6. 验证进程中断、重启后的 `INTERRUPTED`、提交阶段异常、运行中断开元数据库、实例复制后的调度关闭状态。
7. 核对真实数据行数、金额、窗口边界和历史留存；这些是案例验收规则，不写死进通用执行器。
