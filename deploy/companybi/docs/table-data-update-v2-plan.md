# 数据更新二期方案：手写建表 SQL、跨源抽取与成组聚合

日期：2026-10-30

状态：本期代码已实现，真实数据库及数据验收待执行。实际入口、代码验证和验收交接见 `table-data-update-v2-handoff.md`。本文保留设计依据；一期说明见 `table-data-update.md`。

## 1. 要解决的问题

秉坤中间库与新 BI 库处于不同 RDS 实例。需要先将秉坤中用于关联的数据抽取到新 BI 所在 RDS，再用现有 SQL 生成链路关联该 RDS 上其他库的数据，最终生成供仪表板读取的宽表。

采用共享对照表路线：同一来源的必要数据同步一次，供多个下游复用。用户提供的迁移报告指出，「798日报」相关链路目前需要订单关联和员工信息两类对照数据，约 2.7 万行；字段范围、行数和六个下游清单属于案例调查结果，后续按实际血缘验收，不写进产品逻辑。

产品提供三项职责清晰的能力：手写 SQL 创建目标表、查询抽取刷新目标表、按依赖执行聚合 SQL。

## 2. 本期范围与建议

用户已确定：先提供手写建表 SQL 入口，暂缓 SELECT 自动生成结构草稿和可视化结构编辑。

建议本期一起完成以下系统辅助：

1. 建表 SQL 与选定目标数据源、schema、表名的一致性检查。
2. 建表结果确认、真实结构回读，以及失败后的实际状态展示。
3. 抽取查询结果字段与目标表结构的兼容性检查。
4. 可选的小样本查询预览，配合行数、空值、重复主键等运行校验。
5. 成组执行与输入稳定性保护，使多个下游使用同一批共享对照数据。
6. 配置、建表、单表运行和整批运行的状态与审计关联。

这些辅助以减少接错目标、结构不匹配和混用输入批次为目的。保持完整 SQL 编辑能力，便于工作台或 AI 生成 SQL 后直接使用。

本期不加入自动改表、自动推断业务主键、自动删除重建表、URL 触发、自动重试、可视化 ETL 拖拽画布。现有集成中心旧页面继续保留。

## 3. 用户入口与操作流程

### 3.1 数据源中的「数据更新」页签

在现有「数据源配置」「数据源表」旁增加「数据更新」页签，展示归属该目标数据源的任务和任务组。保留表列表中的「数据更新」按钮，直接打开对应任务。

页签提供「新建更新任务」，解决目标表尚未创建时没有操作入口的问题。列表展示目标表、执行方式、所属任务组、调度状态、最近成功时间和最近结果。

### 3.2 新建更新任务

选择目标表方式：使用已有表，或通过 SQL 新建表。

新建表时填写目标表名与建表 SQL；目标数据源和 schema 由当前页面确定。点击「检查建表 SQL」后展示识别出的对象、错误与注意项，再点击「执行建表」。建表成功后回读真实结构，接着配置数据更新。

建表 SQL 与日常刷新 SQL 分开保存。保存刷新配置不会建表；定时执行不会重复执行建表 SQL。离开未保存页面提示保留或放弃草稿。

### 3.3 配置刷新

查询抽取填写查询数据源、SELECT、写入策略、主键或窗口字段，以及允许空结果、超时、行数上限等选项。

SQL 聚合填写在目标数据源执行的完整 SQL 脚本，例如工作台生成的 `run.sql`，并选择上游任务。

任务可独立调度，也可加入任务组。加入组后由组统一触发，页面展示「由任务组调度」和所属组，避免用户在两个位置设置冲突时间。

## 4. 三类 SQL 的使用位置

### 建表 SQL：首次初始化目标表

在新 BI 数据源的建表入口执行 `CREATE TABLE`，定义字段、字段类型、主键和必要索引。建表 SQL 可以来自工作台、AI 或人工编写。

建表入口先覆盖当前正式落地目标 MySQL。现有 PostgreSQL、SQL Server 更新能力保留，可继续选择已有目标表。受管建表能力通过数据库方言接口扩展，页面按支持能力显示入口；不把尚未实现的建表方言显示成可执行选项。

### 抽取 SQL：每晚读取秉坤

例如订单关联查询选择 `BillCode`、`RelateBillCode`，员工查询选择 `EmployeeCode`、`EmployeeName` 并沿用确认过的门店条件。不要把案例筛选条件自动加到用户 SQL 中。

SELECT 在秉坤 SQL Server 连接执行，系统将结果按字段名写入新 BI 的对应表。目标字段名不同，可以在 SELECT 中用 AS 对齐。

### 聚合 SQL：每晚生成宽表

两张对照表都更新成功后，在新 BI 数据源执行日报 `run.sql`，关联该 RDS 上的其他库并生成最终宽表。

跨源抽取每个任务读取一个查询数据源。不同服务器的多源数据先通过各自抽取任务汇集到目标 RDS，再执行聚合任务。

## 5. 手写建表入口的执行规则

### 5.1 建表请求范围

一次请求创建一张目标实表，可包含该表的约束和索引定义，以及针对该表的 CREATE INDEX 语句。所有对象必须属于当前目标 schema 和用户填写的表名。

不接受 CTAS、CREATE TABLE LIKE、跨 schema 对象、DROP、TRUNCATE、ALTER、数据写入、存储过程、客户端命令或动态执行。通过 SQL 语法结构识别语句类型与引用对象，不能仅靠前缀正则判断。无法可靠解析的语法返回明确提示，保留用户输入供修改。

已有表返回「目标表已存在」，提供查看真实结构并使用已有表的入口。IF NOT EXISTS 不能跳过实际结构核对，也不能被当作新表创建成功。

### 5.2 建表与调度分离

建表需要管理员权限，并复用该目标表的互斥控制。请求带唯一操作 ID，重复提交查询同一操作结果；连接中断后不盲目再次执行。

执行前持久化目标对象、SQL 哈希、SQL 版本和操作状态。建表后回读表及索引结构，刷新表列表。真实结构与原 SQL 一起留档，供后续排查。

MySQL DDL 与应用元数据库记录不能组成一个原子事务。若表创建成功但后续索引或记录写入失败，应展示「表已存在、初始化未完成」及已完成步骤，允许重新读取实际状态。对状态不明的操作，先检查目标对象再决定如何处理；不自动删表补偿。

## 6. 系统辅助校验

### 6.1 目标结构回读

展示字段名、数据库类型、长度/精度、可空性、默认值、生成字段、主键和索引。读取成功后生成结构指纹，绑定到任务配置版本。

### 6.2 查询结果兼容性检查

用户主动点击「检查字段」后，以源数据库方言支持的元数据查询或受限只读查询获得结果字段。该动作会访问数据源，页面明确显示来源、超时和限制。

检查结果至少覆盖：重复列名、缺失目标字段、目标必填字段未提供且无默认值、字段类型明显不兼容、字符串长度不足、decimal 精度不足、主键和窗口字段不存在、生成字段写入限制。

检查结论区分通过、需要确认、阻止执行。不能由元数据证明安全的类型转换应说明原因，不自动截断、降精度或更改目标表。运行时仍由暂存写入、事务和数据库约束验证实际值，不能把字段检查当成整批数据必然兼容的证明。

正式执行前再次读取目标结构指纹；发现影响写入的变化时阻止运行并展示差异，要求重新检查并保存配置版本。

### 6.3 小样本预览

提供独立按钮，默认最多返回 20 行，并限制字段长度、总响应体积和执行时间。只展示查询结果，不写入目标表。限制返回行数不代表数据库只扫描同样数量的行，复杂查询仍受超时约束。

预览数据不写入审计日志或运行历史，避免把业务数据复制进配置记录。

### 6.4 正式运行校验

保留现有空结果保护、抽取行数上限、非空/唯一主键、窗口范围、事务写入和取消检查。增加可选的最小行数阈值，适用于不允许骤然缺数的共享对照表。

系统不推断业务主键。例如 BillCode、EmployeeCode 是否唯一，要由实际数据和业务口径确认；只有用户配置主键后才按该规则校验。

来源、业务日期、抽取时间、输入运行 ID 和处理行数记录在任务运行元数据中，不强制向用户目标表添加辅助字段。

## 7. 任务组与同批输入

现有实现检查同一业务日期的上游成功记录，也会保存上游运行 ID；这尚不足以保证整个下游执行过程中共享表没有被下一次刷新覆盖。

本期建议采用任务组串行批次，保持现有 `run.sql` 的表名稳定，避免要求 SQL 生成器改写成每批不同的物理表名。

### 7.1 任务组模型

一个组包含多个抽取/聚合任务及其依赖关系，具有统一的触发设置。组在目标数据源的「数据更新」页签管理；组内抽取任务可读取不同源数据库，写入同一目标数据源下的受管表。

一个任务本期归属至多一个组。多个下游复用同一抽取任务时，放入同一依赖图，抽取任务在每批中只执行一次。依赖检查覆盖缺失节点、环、跨组引用和孤立依赖。

独立任务继续使用原有调度；加入组时明确切换调度归属，停止该任务原有独立触发。组内任务的手动执行入口引导到整组执行，避免绕过批次保护覆盖共享输入。

### 7.2 批次生命周期

1. 手动或定时触发组，确定业务日期与批次 ID，固定组定义、所有任务配置版本及依赖图。
2. 按统一顺序取得本批受管目标表的资源占用。资源申请采用全有或全无的规则，避免多个批次相互等待。
3. 先执行满足条件的抽取任务；只有本批所需上游全部成功，才执行对应聚合任务。
4. 组内下游运行期间，受管共享表保持占用状态，下一批、独立更新和建表操作均不能覆盖它们。读取报表不受这个应用层占用控制影响。
5. 任一任务失败，停止派发新节点，等待或取消已运行节点并记录结果；确认本批执行退出后，再释放资源占用。
6. 失败后默认新建一批重跑，重新抽取输入。暂不提供跨批次复用旧成功节点的自动断点续跑，以免混用已被覆盖的物理数据。

所有依赖只认可本批成功节点，不能用另一批同业务日期的成功记录替代。

### 7.3 中断与一致性边界

资源占用与批次状态需要持久化，并配合会话锁、存活检查和提交前检查。进程中断的批次标为待核查，不因超时就直接放开目标表写入；确认旧执行已经终止后再解除占用。组运行期间的配置编辑形成下一版本，当前批次继续使用原快照。

这保证的是组内下游消费期间共享输入稳定。两个秉坤查询仍各有自己的抽取时刻；它们不自动获得源库同一事务快照。若业务需要源库严格同一时刻快照，应另行设计源端快照读取能力。

每张目标表按自己的事务提交，六张输出宽表不承诺同时原子发布。若后面的聚合失败，前面已经成功的输出可能已更新，批次页面必须明确显示这些表的状态。全组输出同时切换属于后续独立能力。

应用层占用覆盖本功能管理的写入任务。旧 ETL、外部脚本和数据库直写需要在接管对应表之前停止或调整；不能声称应用锁能阻止外部写入。

## 8. 秉坤案例配置方式

首次创建订单关联对照表和员工对照表，建议用名称体现用途，例如 `pekon_order_relation` 与 `pekon_employee_lookup`。字段类型、长度、主键与门店/空值筛选沿用经过核对的业务口径。

建立「线下零售」任务组，加入两个全量抽取任务和实际确认的日报聚合任务。六个下游共享两个抽取结果，依赖关系按现有 SQL 的实际读表关系配置。报告所列六个输出用于验收，不作为预置节点写进产品。

批次按组设置时间。成功后，仪表板继续读取新 BI 宽表。秉坤临时不可用时，抽取失败阻止本批下游运行，报表继续读取已有宽表，并可在更新页面看到最近成功时间。

## 9. 代码改造安排

第一步：新增数据源级数据更新页签、新建任务入口、受管建表服务和建表操作记录，复用已有目标表配置抽屉。

第二步：增加数据库方言能力声明、结构元数据读取、查询字段检查、小样本预览、结构指纹和最小行数校验。抽取执行器继续采用暂存与事务写入。

第三步：新增任务组定义、批次及节点记录、资源占用模型；扩展调度与运行器，使组内依赖按批次判断，并加入组级运行页面。

第四步：完成权限、审计、取消、重复提交、进程中断与错误状态收敛，补充使用说明和验收清单。

已有独立更新任务保持兼容；是否加入组由用户明确操作。新旧功能不自动迁移、不自动改动业务表结构。

## 10. 验证和交付标准

本次实现工作的验证范围继续遵循用户要求：源码编译、静态检查、单元测试，以及使用 JDBC 替身的流程测试。真实数据库连接、建表、数据抽取、金额/行数对账和部署由后续验收执行者完成。

代码测试重点：DDL 对象约束与语句解析、重复请求、DDL 部分成功、结构兼容性判断、预览限制、运行前结构变化、依赖环、配置版本快照、同批依赖、跨批互斥、取消/失败后资源释放、进程中断后的占用处理、权限和审计。

后续真实验收先用任意名称的测试表验证通用能力，再用秉坤订单/员工对照表和日报链路验收。检查本批两个输入只抽取一次、下游不会引用上一批输入、失败状态清楚、既有宽表历史留存符合原业务规则。

交付时分别报告代码验证结果和真实数据验收状态，避免把两类验证混为一谈。
