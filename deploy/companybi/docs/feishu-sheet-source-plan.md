# 飞书电子表格接入、存储与更新完整方案

日期：2026-11-02

状态：已有数据库落库模式已实施并通过代码级检查；BI 托管独立数据源暂缓。实际交付范围与验收交接见 `feishu-sheet-source-handoff.md`。业务验收信息来自用户提供的报告；本轮未查询现网配置或数据库。

## 1. 产品目标

支持从零添加新的飞书电子表格来源，选择工作表、读取范围和数据存储位置，完成首次同步，然后持续更新并驱动下游 SQL。业务操作不依赖迁移工作台、external_inputs.json 或命令行。

完整操作链路：添加来源 → 选择应用连接和工作表 → 选择存储位置 → 确认字段与目标结构 → 预览校验 → 首次同步 → 创建数据集或配置下游 SQL → 日常更新与运行观察。

## 2. 已核实的代码现状

- DataEase 已有 Excel/ExcelRemote 数据源表单、表列表及远程更新入口，可以复用页面组织方式。飞书表格需要独立连接器：处理应用认证、spreadsheet/sheet 标识、工作表枚举和范围读取，不将表格网页 URL 直接交给远程 Excel 下载器。
- company_feishu_source 已保存来源、目标库表、schema_json、调度和最近成功时间。旧模块还存在特定门店种子配置、开发目录环境文件和隧道依赖，需要从正式执行路径中移除。
- 当前随 BI 交付的 Node 执行器通过私有进程通信运行，嵌入式调度显式排除了 sheet sources。部署 BI 并不自动接管原表格同步任务。
- 数据更新已有目标数据源入口、手写 DDL、SQL/查询抽取任务及任务组。新增来源类型和首次接入流程可以与这些能力衔接。
- 四张历史飞书表的实际调度、执行器归属和新鲜度尚待读取真实配置确认。

## 3. 来源、存储、展示三个概念

飞书应用连接负责认证；电子表格来源记录 URL、工作表和读取规则；存储目标决定数据实际写入哪里。数据源树的展示位置不改变物理存储位置。

一个电子表格可以包含多个工作表。首版每个所选工作表对应一个独立同步任务和一张目标表；允许在向导中逐项配置，多工作表合并成一张表后续另做。

一个同步任务只有一个明确的写入目标。多个下游复用该目标表，不为每个下游复制同步任务。修改存储模式或目标数据库属于显式迁移，不是普通配置保存。

## 4. 入口与导航

### 4.1 添加数据源

在现有文件、远程 Excel/CSV 等选项旁新增「飞书电子表格」。共享接入向导的视觉结构，保留独立类型、认证和读取逻辑。

步骤：

1. 填写来源名称，选择已有飞书应用连接；具备连接管理权限时可创建连接后返回。
2. 粘贴电子表格 URL，获取可访问的工作表，选择要接入的工作表。
3. 配置表头行、数据起止行、列范围。结束行空表示读取有效数据末尾。
4. 选择存储模式及具体目标，确认字段映射、类型、精度和空值规则。
5. 预览和校验；展示将创建/接管的目标对象及更新方式。
6. 保存配置，可选择立即首次同步。独立显示「已保存、未同步」与「首次同步成功」。
7. 成功后提供「查看目标表」「创建数据集」「配置数据更新」「加入任务组」入口。

### 4.2 已有数据库内添加

在数据库数据源的「数据源表」和「数据更新」页提供「接入外部数据 → 飞书电子表格」。打开相同向导，预选当前数据源作为存储目标。

这解决用户已经在新 BI 库内、但目标表尚不存在时的新增需求。

### 4.3 日常管理

- 独立飞书来源展示应用连接名称、URL、工作表、读取范围及存储位置，提供跳转目标表。
- 同步到已有数据库的表归属该数据库表列表，标注「来源：飞书」，可打开同一份来源配置。
- 「数据更新」统一展示手动、定时、组调度、状态、历史和错误。来源入口和目标表入口编辑同一任务。
- 集成中心保留共享应用凭据管理；表格任务配置放在数据准备流程内。

## 5. 两种存储模式

### A. 同步到已有数据库（本项目优先实现）

选择有写入授权的目标数据源、数据库/schema 和表。首期发布能力限定为 MySQL，具体数据库名称由配置决定。

飞书数据落到用户选择的业务数据库。选择新 BI 数据源后，可以直接在该 RDS 的 SQL 中关联落库表及同实例其他有权限的库；下游使用现有 run.sql 或数据更新 SQL 任务。

在目标表页展示来源信息即可。若希望左侧同时保留飞书来源条目，它是管理来源的入口，引用同一落库表，不另建一份数据库副本或第二个拥有独立调度的任务。

### B. 作为独立飞书数据源，由 BI 托管存储

用户不选择业务数据库，由产品管理表格副本，并像文件数据源一样创建数据集。必须实现完整的数据源查询、权限、备份、容量及清理生命周期，不能仅增加一个树节点。

应先核实并复用现有文件数据源的托管存储能力；不将应用元数据库默认当作业务数据落点。具体物理存储方案需实现前评估确认。

此模式下，新 BI RDS 中的 run.sql 不能直接读取 BI 托管副本。要加入现有 SQL 链路，应显式迁移/同步到已有数据库模式，并核对下游引用。

两种模式都属于完整产品设计；建议先交付 A 的完整流程，B 的交付时间待用户确认。未完成的模式不展示为可执行入口。

## 6. 字段、建表与预览

- 新表沿用已确定的手写建表 SQL 能力；飞书字段与建表后的实际结构映射，回读类型和索引。已有表读取结构后检查兼容性。
- 飞书预览展示字段、样本、类型建议、已读取行数和是否完成全量读取。抽样数量不能冒充总行数。
- SELECT 自动生成结构草稿仍不在既定范围；飞书是否增加可视化字段建表可单独讨论，不作为首版接入前提。
- 字段重命名、必填约束、decimal 精度、小数位、日期格式及空值标记显式保存。字符串 None 是否转空由用户配置，默认不静默丢行、取整或将错误值变为零。
- 约定字段缺失、重复表头、无法转换或超出目标容量时阻止发布，指出具体字段和行号。新增源字段提示待处理，不自动改变目标表结构。
- 预览绑定配置版本和有效期；修改连接、范围、映射、目标结构后重新预览。运行时校验完整数据。
- 首版支持电子表格 Sheets URL；wiki、多维表格、附件等明确提示类型不支持。不实现公式计算引擎；API 返回公式单元格时的处理方式需在连接器中明确验证并展示。

## 7. 同步、调度与 SQL 依赖

- 飞书首版采用整表快照更新。新快照写入唯一暂存表，验证结构、行数及约束后发布，失败保留最近成功快照。
- 沿用目标表约定的类型、索引和精度，避免每次根据样本重新推断结构。原子换表需检查外键、触发器等对象是否兼容，不支持的目标明确拒绝。
- 支持手动、每日时间及时区、任务组依赖触发。加入任务组后，由组统一调度，不再同时运行独立每日计划。
- 飞书同步成为可等待完成的组节点：成功回执必须代表目标快照已发布；失败阻断依赖节点。共享上游每批只执行一次。
- 飞书写入和 SQL 写入使用一致的目标占用机制。组从抽取到下游完成期间保护共享输入，独立飞书调度不能中途覆盖。
- 调度、配置版本、排队/运行记录由统一任务管理层负责；Node 执行器负责飞书读取和同步执行。旧 sheet scheduler 接管后停止发起同一任务，避免双调度。
- 取消、中断、发布结果未知要区分：发布前可取消；无法确认发布结果时进入待核查，保留占用并检查目标状态，不能直接重放。

## 8. 状态、权限和记录

任务列表显示：来源、工作表、存储模式、目标库表、调度归属、上次执行结果、最近成功时间、成功行数、下一计划、是否超期。

运行历史记录：配置版本、业务日期、触发方式、计划/开始/结束时间、执行节点、读/写行数、字段数、校验结果、发布结果、脱敏错误。失败状态和旧快照时间同时保留。

启用每日计划的任务依据应到计划判断超期；仅手动任务显示成功时间，也可配置期望更新间隔，不强行推断过期。同步时间和源数据业务日期范围分开展示。

创建/修改任务、手动运行、接管目标表、管理应用凭据分别检查能力；执行前核对任务身份、目标写入权限及连接状态。后台复用 BI 数据源凭据管理，不保存第二套明文 WRITE_DB_*。

删除同步配置默认保留数据表并检查下游依赖；删除物理数据是独立明确操作。更换目标或源工作表需重新校验并保留版本历史。

## 9. 持久化与历史接管

company_feishu_source 保留现有 ID 和来源配置，按需扩展应用连接 ID、目标数据源 ID、存储模式、版本和接管状态。统一更新任务通过 source ID 引用；调度与运行状态只保留一个权威写入方，旧字段通过迁移兼容处理，避免两套可编辑配置。

开发接管前由验收环境读取四张表的实际 source 记录、调度、成功时间、日志、目标结构和执行器归属。核对主键/索引/decimal/日期等差异，绑定现有目标及应用连接，不自动触发同步。

接管顺序：记录旧配置与运行位置 → 停止旧任务新调度并等待在途结束 → 建立新配置引用 → 验证读取和目标约定 → 手动验收 → 开启新计划。external_inputs.json 保留原映射，日常业务配置不依赖它。

## 10. 交付和验收

第一阶段：新增入口和数据库落库模式、保存草稿、手写建表/接管已有表、预览、首次同步、字段规则和历史查询。

第二阶段：每日计划、任务组依赖、统一目标占用、取消/中断/未知结果核查，以及四张历史表接管。完成前两阶段才构成可交付的业务闭环。

第三阶段：如确认需要 BI 托管独立数据源，接入相应存储、查询、权限和生命周期；复用相同飞书连接器和更新配置流程。

验收必须包含全新飞书表从零接入，不只验证既有四张表。覆盖两种入口指向同一任务、多个工作表独立落表、decimal 小数、None/空值、字段变化、空结果、失败保留旧数据、重复触发、依赖阻断和重启恢复。最后用 798 日报案例对账，业务字段和筛选条件仅出现在配置中。

## 11. 已确认决策与实现调整

1. 首次交付同步到已有 MySQL 数据源；BI 托管独立数据源暂缓。
2. 新增数据源页面提供飞书接入入口；目标数据源表列表标注飞书来源，通过数据更新管理同一份配置。
3. 使用 MySQL 临时表校验，再在 InnoDB 事务内替换目标内容，保留目标表结构、索引与授权。提交结果未知时保留占用并进入待核查。
4. 本轮执行代码级检查。四张历史来源的配置核查、停止旧调度、真实接管及业务对账交给后续环境验收。
